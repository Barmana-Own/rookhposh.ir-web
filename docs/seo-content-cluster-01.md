## خلاصه اجرایی

خوشه پیشنهادی باید از جایگاه واقعی رخ‌پوش شروع شود: سایت در سورس فعلی هم تجربه پرو مجازی برای کاربر را توضیح می‌دهد و هم صفحه تجاری جداگانه برای فروشگاه‌های آنلاین و پلن‌های قیمت‌گذاری دارد. بر اساس نقشه معماری فعلی، پیشنهاد اصلی حفظ نقش B2B/store-first برای صفحات تجاری است و محتوای مصرف‌کننده فقط زمانی توسعه پیدا کند که مالک محصول ارائه مستقیم به مصرف‌کننده را تأیید کند.

این سند مقاله‌ای تولید نمی‌کند، URL جدیدی به sitemap اضافه نمی‌کند و هیچ ادعای حجم جست‌وجو، رتبه، نرخ تبدیل، کاهش مرجوعی، دقت سایز، پیش‌بینی فیت، هوش مصنوعی یا اتصال فنی فروشگاه را تأییدشده فرض نمی‌کند.

## وضعیت فعلی سایت و موجودی مقاله

### سورس repository

- صفحه `/` نقش معرفی دسته/محصول و روایت اصلی تجربه را دارد.
- `/for-online-stores/` برای مخاطب فروشگاه‌های آنلاین است و به قیمت‌گذاری و CTA dashboard وصل می‌شود.
- `/how-it-works/` توضیح مرحله‌ای گردش‌کار است.
- `/pricing/` نقش مقایسه پلن و تصمیم تجاری دارد.
- `/faq/` پاسخ‌های پشتیبانی و رفع ابهام است.
- `/blog/` در نبود `BLOG_CONTENT_API_URL` empty state صادقانه و بدون مقاله جعلی نشان می‌دهد.
- provider مقاله فقط رکوردهای معتبر و منتشرشده را مصرف می‌کند؛ draft، `noindex` و محتوای نامعتبر نباید وارد sitemap/feed شوند.
- CMS در repository جداگانه قرار دارد و این سایت مالک authoring یا database نیست.

### مشاهده host عمومی فعلی

در بازدید کنترل‌شده از `https://rookhposh.ir/`، عنوان و navigation نسخه قدیمی، لینک‌های hash و لینک Blog خارجی مشاهده شد. `/blog/` پس از redirect به `/blog` پاسخ 404 داد. همچنین در بررسی HTTP، `/for-online-stores/`، `/how-it-works/`، `/pricing/` و `/faq/` پس از redirect به مسیر بدون slash پاسخ 404 دادند و `/robots.txt` و `/sitemap.xml` نیز 404 بودند. `blog.rookhposh.ir` در محیط بررسی با `ERR_NAME_NOT_RESOLVED` باز نشد.

نتیجه عملی: قبل از انتظار برای کشف مقاله یا تحلیل عملکرد live، build تأییدشده باید روی host عمومی deploy شود و سپس sitemap، Blog و canonicalهای live دوباره بررسی شوند. این finding از Prompt 04/10 است و به‌تنهایی دلیل تولید مقاله بیشتر نیست.

## راهنمای editorial و محدودیت‌های ادعا

مبنای تولید محتوا باید people-first و مبتنی بر تجربه یا اطلاعات قابل اثبات باشد. [راهنمای Google برای محتوای helpful و people-first](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) تولید تعداد زیادی صفحه برای پوشش variationهای جست‌وجو را توصیه نمی‌کند. [راهنمای SEO Starter گوگل](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) نیز روی عنوان‌های واضح، لینک‌های مرتبط و توصیف دقیق محتوای همان صفحه تأکید دارد.

قواعد اختصاصی رخ‌پوش:

- «پیش‌نمایش لباس روی تصویر» از source قابل استفاده است؛ «پیش‌بینی فیت واقعی»، «دقت سایز»، «کاهش قطعی مرجوعی» و «انتخاب مطمئن‌تر به‌عنوان نتیجه تضمین‌شده» قابل استفاده نیستند مگر evidence/approval اضافه شود.
- «برای فروشگاه‌های آنلاین» از source و route موجود است؛ ادعای نصب افزونه، API، ویجت، اتصال ووکامرس، SLA، پنل یا حجم مشخص فروشگاه در source عمومی این repository اثبات نشده است.
- «هوش مصنوعی» در seed و SERP دیده شد، اما استفاده از آن برای رخ‌پوش نیازمند تأیید محصول/فنی است. وجود نتیجه‌های رقیب evidence capability رخ‌پوش نیست.
- قیمت‌های صفحه `/pricing/` فقط در مقاله قیمت‌گذاری و پس از تأیید به‌روز بودن owner بازاستفاده شوند؛ مقاله نباید رقم جدید، تخفیف یا مقایسه ساختگی اضافه کند.
- درباره تصویر کاربر، نگهداری تصویر، حذف خودکار، حریم خصوصی یا امنیت فقط متن approved/legal یا رفتار واقعی CMS/public API ملاک است. متن binding legal تولید نشود.
- هر مقاله باید author، تاریخ، منابع، scope و در صورت نیاز disclosure روش تولید را واقعی نگه دارد؛ bio یا تجربه ساختگی اضافه نشود.

## شکاف محتوا و فرصت لینک داخلی

### شکاف‌های قابل اقدام

1. Blog اول‌شخص در source آماده است اما در محیط فعلی مقاله منتشرشده ندارد؛ نخستین مقاله باید قبل از article cluster به CMS متصل و در live بررسی شود.
2. برای store-owner، صفحه `/for-online-stores/` وجود دارد اما checklist ارزیابی خرید و پرسش‌های فنی/عملیاتی مستقل ندارد.
3. برای کاربر، FAQ و how-it-works وجود دارد اما یک راهنمای عملی آماده‌سازی تصویر می‌تواند در صورت تأیید محدودیت‌ها ارزش افزوده بدهد.
4. داده Search Console، query/page performance و crawl/indexing واقعی در دسترس نیست؛ اولویت‌بندی بر اساس volume یا CTR مجاز نیست.
5. مدرک first-party درباره نتیجه تجاری، نرخ بازگشت، دقت فیت، AI، privacy retention و integration باید پیش از استفاده محتوایی ثبت شود.

### لینک‌سازی پیشنهادی

- `/for-online-stores/` ← buyer guide و checklist؛ anchor طبیعی مانند «راهنمای ارزیابی سرویس پرو مجازی برای فروشگاه».
- `/how-it-works/` ← راهنمای آماده‌سازی تصویر؛ anchor «مراحل و شرایط شروع تجربه» فقط در صورت تأیید conditions.
- `/pricing/` ← راهنمای انتخاب پلن؛ anchor «جزئیات پلن‌ها و اعتبارها».
- `/faq/` ← مقاله‌های how-to؛ anchorهای پرسشی طبیعی، نه تکرار exact-match در همه صفحات.
- هر مقاله ← یک CTA متناسب: صفحه store، pricing، FAQ یا dashboard؛ CTA واحد و تکراری برای همه intentها استفاده نشود.
- Blog index ← دسته‌ها/مقالات واقعی؛ از ساخت category page خالی یا tag page indexable خودداری شود.

## briefهای پیشنهادی مقاله

این briefها سفارش تولید متن کامل نیستند. هر brief تا زمان تکمیل evidence و owner review در وضعیت `PLANNED` باقی می‌ماند.

### ۱. راهنمای ارزیابی اتاق پرو مجازی برای فروشگاه اینترنتی

- **اولویت/وضعیت:** P1 — `PLANNED; B2B`
- **intent و مخاطب:** commercial investigation برای صاحب یا مدیر فروشگاه آنلاین پوشاک.
- **خوشه موضوعی:** `اتاق پرو مجازی برای فروشگاه اینترنتی`؛ زیرموضوع انتخاب راهکار.
- **عنوان پیشنهادی:** «راهنمای ارزیابی اتاق پرو مجازی برای فروشگاه اینترنتی».
- **پرسش‌های پشتیبان:** چه مسئله‌ای را حل می‌کند؟ چه ورودی‌هایی لازم است؟ پیش از انتخاب سرویس چه چیزهایی را باید از provider پرسید؟ روند آزمایش و سنجش کیفیت چگونه تعریف شود؟ چه ملاحظات حریم خصوصی و محتوایی باید بررسی شود؟
- **outline:** تعریف مسئله؛ تفاوت preview تصویری با ادعای fit/size؛ checklist ورودی و خروجی؛ پرسش‌های فنی و عملیاتی؛ روش اجرای pilot؛ جمع‌بندی و مسیر اقدام.
- **منابع/evidence لازم:** product owner درباره مدل سرویس؛ نمونه واقعی workflow؛ محدودیت‌های ورودی/خروجی؛ پاسخ approved درباره privacy و retention؛ هر integration فقط با مستند واقعی.
- **لینک داخلی:** `/for-online-stores/`، `/how-it-works/`، `/pricing/`، `/faq/`.
- **هدف conversion:** هدایت تصمیم‌گیرنده به صفحه store و سپس dashboard، فقط با CTA تأییدشده.
- **claimهای نیازمند owner:** integration، پنل، plugin/API، KPI، کاهش مرجوعی، دقت و هر guarantee.

### ۲. قبل از شروع پرو مجازی چه تصویری آماده کنیم؟

- **اولویت/وضعیت:** P1 — `PLANNED; consumer/operator`
- **intent و مخاطب:** how-to برای کاربری که می‌خواهد تجربه را شروع کند؛ می‌تواند برای operator فروشگاه نیز کاربرد داشته باشد.
- **خوشه موضوعی:** `پرو مجازی لباس` و آماده‌سازی تصویر.
- **عنوان پیشنهادی:** «قبل از شروع پرو مجازی لباس چه تصویری آماده کنیم؟»
- **پرسش‌های پشتیبان:** تصویر واضح یعنی چه؟ چرا تمام‌قد و رو‌به‌دوربین بودن در source فعلی آمده است؟ چه چیزی باعث می‌شود preview قابل بررسی باشد؟ در صورت نامناسب بودن تصویر چه مسیر جایگزینی وجود دارد؟
- **outline:** هدف تصویر ورودی؛ checklist کوتاه؛ خطاهای رایج بدون وعده کیفیت؛ مرحله انتخاب لباس؛ دیدن preview؛ لینک به FAQ.
- **منابع/evidence لازم:** رفتار واقعی runtime/product؛ تست‌های UX؛ محدودیت فایل/فرمت/حجم اگر وجود دارد؛ متن approved برای داده تصویر.
- **لینک داخلی:** `/how-it-works/`، `/faq/`، `/for-online-stores/`.
- **هدف conversion:** ورود به تجربه یا مشاهده مسیر how-it-works؛ dashboard فقط اگر CTA برای کاربر نهایی approved باشد.
- **claimهای نیازمند owner:** حذف تصویر، نگهداری، محرمانگی، زمان تولید، تضمین کیفیت و هر اصطلاح AI.

### ۳. پرو مجازی لباس چیست و چه چیزی را در تصویر نشان می‌دهد؟

- **اولویت/وضعیت:** P1 — `PLANNED; informational`
- **intent و مخاطب:** کاربری که category را می‌شناسد اما تفاوت preview تصویری با خرید/فیت واقعی را نمی‌داند؛ مخاطب عمومی و store-owner هر دو، با تفکیک CTA.
- **خوشه موضوعی:** `اتاق پرو مجازی` و `پرو مجازی لباس`.
- **عنوان پیشنهادی:** «پرو مجازی لباس چیست؟ راهنمای ساده دیدن لباس روی تصویر».
- **پرسش‌های پشتیبان:** پرو مجازی چه کاری انجام می‌دهد؟ ورودی و خروجی چیست؟ چه تفاوتی با پرو حضوری یا جدول سایز دارد؟ چه چیزهایی را نباید از preview نتیجه گرفت؟
- **outline:** تعریف بی‌طرفانه؛ گردش‌کار رخ‌پوش بر اساس facts؛ مزیت قابل‌بیان در حد مشاهده تصویر؛ محدودیت‌های claim؛ مسیر بعدی برای مصرف‌کننده و فروشگاه.
- **منابع/evidence لازم:** تعریف product-approved؛ screenshot/output واقعی؛ محدودیت fit/size؛ بررسی حقوقی/حریم خصوصی در صورت اشاره به تصویر.
- **لینک داخلی:** `/`، `/how-it-works/`، `/for-online-stores/`، `/faq/`.
- **هدف conversion:** تقسیم روشن به «آشنایی با مراحل» و «راهنمای فروشگاه»؛ نه CTA تجاری واحد برای همه.
- **claimهای نیازمند owner:** «AI»، «دقت»، «واقعی»، «پیش‌بینی سایز»، کاهش ریسک/مرجوعی و هر نتیجه خرید.

### ۴. چک‌لیست آماده‌سازی محتوای لباس برای پیش‌نمایش آنلاین

- **اولویت/وضعیت:** P1 — `PLANNED; B2B`
- **intent و مخاطب:** operator یا تیم محتوای فروشگاه که می‌خواهد بداند برای آماده‌سازی لباس چه assetهایی لازم است.
- **خوشه موضوعی:** store-owner / catalog readiness.
- **عنوان پیشنهادی:** «چک‌لیست آماده‌سازی محتوای لباس برای پیش‌نمایش آنلاین».
- **پرسش‌های پشتیبان:** عکس محصول چه ویژگی‌هایی داشته باشد؟ نام‌گذاری و دسته‌بندی چگونه کنترل شود؟ چه خروجی‌ای برای بررسی داخلی لازم است؟ چگونه نمونه آزمایشی انتخاب کنیم؟
- **outline:** هدف checklist؛ assetهای لازم؛ کنترل کیفیت تصویر؛ نمونه‌گیری؛ ثبت feedback؛ handoff به provider.
- **منابع/evidence لازم:** فقط specification واقعی CMS/product؛ نمونه asset approved؛ فرآیند واقعی فروشگاه یا pilot. در نبود این facts، مقاله به checklist عمومی محدود شود.
- **لینک داخلی:** `/for-online-stores/`، `/how-it-works/`، `/faq/`.
- **هدف conversion:** درخواست demo/ورود dashboard بعد از تأیید owner.
- **claimهای نیازمند owner:** فرمت/رزولوشن/حجم، catalog import، API، plugin، زمان پردازش و کیفیت خروجی.

### ۵. پرسش‌هایی که قبل از انتخاب سرویس پرو مجازی باید از provider بپرسیم

- **اولویت/وضعیت:** P2 — `PLANNED; B2B`
- **intent و مخاطب:** buyer با intent مقایسه و کاهش uncertainty پیش از تماس یا خرید.
- **خوشه موضوعی:** commercial investigation؛ هم‌راستا با `اتاق پرو مجازی برای فروشگاه اینترنتی` بدون تکرار صفحه تجاری.
- **عنوان پیشنهادی:** «پیش از انتخاب سرویس پرو مجازی، چه سؤال‌هایی از ارائه‌دهنده بپرسیم؟»
- **پرسش‌های پشتیبان:** مدل قیمت‌گذاری چیست؟ محدودیت خروجی و asset چیست؟ داده تصویر چگونه مدیریت می‌شود؟ تست آزمایشی چگونه سنجیده می‌شود؟ پشتیبانی و rollback چگونه است؟
- **outline:** checklist خرید؛ سؤال‌های محصول؛ سؤال‌های فنی؛ سؤال‌های privacy/operations؛ طراحی pilot؛ template تصمیم‌گیری.
- **منابع/evidence لازم:** این مقاله می‌تواند عمومی باشد، اما هر بخش درباره رخ‌پوش باید به contract و documentation واقعی ارجاع دهد.
- **لینک داخلی:** `/for-online-stores/`، `/pricing/`، `/faq/`.
- **هدف conversion:** مشاهده صفحه store یا تماس/CTA موجود؛ contact workflow جداگانه فعلاً در source ساخته نشده است.
- **claimهای نیازمند owner:** SLA، پشتیبانی، integration، security certification، retention و KPI.

### ۶. راهنمای انتخاب پلن پرو مجازی برای فروشگاه‌ها

- **اولویت/وضعیت:** P2 — `PLANNED; pricing`
- **intent و مخاطب:** commercial investigation برای تصمیم‌گیرنده‌ای که پلن‌ها و ظرفیت را مقایسه می‌کند.
- **خوشه موضوعی:** pricing/commercial investigation.
- **عنوان پیشنهادی:** «چطور پلن پرو مجازی مناسب فروشگاه را انتخاب کنیم؟»
- **پرسش‌های پشتیبان:** تفاوت دوره‌ها و اعتبارها چیست؟ پیش از انتخاب چه حجم استفاده‌ای را باید برآورد کرد؟ چه سؤالاتی را باید از dashboard یا provider پرسید؟
- **outline:** تعریف واحدهای قیمت فعلی؛ روش برآورد مبتنی بر داده داخلی owner؛ مقایسه بی‌طرفانه پلن‌ها؛ FAQ؛ CTA صفحه pricing.
- **منابع/evidence لازم:** ارقام و شرایط live صفحه `/pricing/`؛ تعریف دقیق «پرو/اعتبار»؛ تغییرات billing و تأیید owner در زمان انتشار.
- **لینک داخلی:** `/pricing/`، `/for-online-stores/`، `/faq/`.
- **هدف conversion:** مشاهده pricing و در صورت تأیید، ورود به dashboard.
- **claimهای نیازمند owner:** «به‌صرفه»، «بهترین»، forecast فروش، تخفیف، تمدید، rollover و هر توصیه مبتنی بر حجم بدون داده داخلی.

### ۷. گردش‌کار پرو مجازی برای فروشگاه آنلاین از تصویر تا بررسی نتیجه

- **اولویت/وضعیت:** P2 — `PLANNED; workflow`
- **intent و مخاطب:** مخاطبی که قبل از ورود می‌خواهد sequence را بفهمد؛ store-owner و end-user در دو بخش جدا.
- **خوشه موضوعی:** informational/how-to؛ مکمل `/how-it-works/` نه تکرار آن.
- **عنوان پیشنهادی:** «گردش‌کار پرو مجازی برای فروشگاه آنلاین؛ از انتخاب لباس تا بررسی تصویر».
- **پرسش‌های پشتیبان:** مراحل تجربه چیست؟ نقش تصویر کاربر و انتخاب لباس چیست؟ در کدام مرحله باید نتیجه را بررسی کرد؟ چه چیزی خارج از scope preview است؟
- **outline:** سناریوی کوتاه؛ ورودی؛ انتخاب؛ preview؛ مقایسه مدل/رنگ در حد source؛ تصمیم؛ محدودیت‌ها و FAQ.
- **منابع/evidence لازم:** داده واقعی workflow و خروجی؛ مشاهده UX؛ عدم استفاده از claim فیت/سایز مگر approved.
- **لینک داخلی:** `/how-it-works/`، `/for-online-stores/`، `/faq/`.
- **هدف conversion:** هدایت به route مناسب بر اساس نقش مخاطب.
- **claimهای نیازمند owner:** integration در storefront، automation، AI، حفظ نتیجه، اشتراک‌گذاری و نتیجه خرید.

### ۸. پرو لباس با هوش مصنوعی: چه چیزهایی را باید از یک preview تصویری انتظار داشت؟

- **اولویت/وضعیت:** P3 — `HOLD_FOR_OWNER_VERIFICATION`
- **intent و مخاطب:** technology-curious یا consumer که با عبارت AI وارد می‌شود.
- **خوشه موضوعی:** `پرو لباس با هوش مصنوعی`؛ informational و claim-sensitive.
- **عنوان پیشنهادی:** فقط پس از تأیید: «پرو لباس با هوش مصنوعی؛ تفاوت پیش‌نمایش تصویری با ادعای تناسب لباس».
- **پرسش‌های پشتیبان:** preview تصویری چه چیزی را نشان می‌دهد؟ آیا با سایز یا fit واقعی یکی است؟ کاربر چه ورودی‌ای می‌دهد؟ چه محدودیت‌هایی باید شفاف گفته شود؟
- **outline:** تعریف اصطلاحات؛ مرزبندی visual preview و fit prediction؛ روش ارزیابی output؛ ملاحظات داده؛ لینک به facts واقعی رخ‌پوش.
- **منابع/evidence لازم:** سند فنی و product approval درباره AI، مدل، fit/size، داده تصویر، retention و محدودیت output.
- **لینک داخلی:** فعلاً `/how-it-works/` و `/faq/` فقط اگر متن آن‌ها با مقاله سازگار و approved باشد.
- **هدف conversion:** آگاهی و سپس route مناسب؛ CTA تجاری تا زمان تأیید capability محدود بماند.
- **claimهای نیازمند owner:** تمام عنوان و تقریباً تمام assertions فنی این brief؛ بدون approval منتشر نشود.

## اولویت انتشار پیشنهادی

این ترتیب بر اساس تفاوت intent، نزدیکی به معماری موجود و آمادگی evidence است؛ هیچ ادعای traffic یا احتمال ranking در آن وجود ندارد.

1. **پیش‌نیاز عملیاتی — P0:** deploy نسخه تأییدشده public site، فعال‌سازی CMS، اعمال migration روی MySQL مجاز، اتصال provider و recheck live `/blog/`، sitemap و feed. تا این مرحله، مقاله indexable منتشر نشود.
2. **راهنمای ارزیابی اتاق پرو مجازی برای فروشگاه اینترنتی — P1:** نزدیک‌ترین gap به صفحه B2B و دارای conversion مسیرمند، مشروط به evidence product.
3. **قبل از شروع پرو مجازی چه تصویری آماده کنیم؟ — P1:** سؤال عملی مشخص و قابل اتصال به how-it-works/FAQ؛ مشروط به تأیید محدودیت‌های واقعی ورودی.
4. **پرو مجازی لباس چیست؟ — P1:** مقاله category برای Blog، با مرزبندی روشن preview در برابر fit/size و بدون ادعای AI.
5. **چک‌لیست آماده‌سازی محتوای لباس — P1/P2:** فقط پس از دریافت specification واقعی asset/catalog.
6. **راهنمای سؤال‌های خرید از provider — P2:** محتوای evergreen و کم‌ریسک‌تر، با CTA غیراغراق‌آمیز.
7. **راهنمای انتخاب پلن — P2:** پس از تأیید قیمت و semantics واحدهای مصرف در production.
8. **گردش‌کار مکمل how-it-works — P2:** فقط اگر تجربه یا evidence مستقلی به route فعلی اضافه کند؛ در غیر این صورت منتشر نشود.
9. **مقاله AI/fit — P3/HOLD:** تا زمان owner verification منتشر نشود.

## تصمیم‌های لازم از مالک محصول

| تصمیم | اثر بر cluster |
| --- | --- |
| آیا homepage و محتوای اصلی B2B/store-first باقی می‌ماند؟ | تعیین CTA و تفکیک مقاله‌های مصرف‌کننده از store-owner |
| آیا رخ‌پوش واقعاً برای کاربر نهایی مستقل از فروشگاه قابل استفاده است؟ | تعیین مجاز بودن cluster مصرف‌کننده و `/for-consumers/` |
| آیا اصطلاح «هوش مصنوعی» برای محصول approved است؟ | تعیین امکان brief شماره ۸ |
| آیا محصول fit/size prediction دارد یا فقط visual preview؟ | تعیین واژگان مجاز و حذف claims پرریسک |
| محدودیت واقعی تصویر ورودی، زمان خروجی و retention چیست؟ | تعیین briefهای ۲، ۳ و ۴ |
| integrationهای واقعی CMS/dashboard/storefront کدام‌اند؟ | تعیین briefهای B2B و هر مقاله integration |
| قیمت، اعتبار، تمدید و شرایط پلن live و approved هستند؟ | تعیین brief شماره ۶ |
| privacy/terms approved چه زمانی ارائه می‌شوند؟ | تعیین امکان مقاله‌های داده/حریم خصوصی و لینک legal |

## وضعیت داده و نتیجه نهایی

- داده‌های Search Console: `SEARCH CONSOLE ACCESS REQUIRED`.
- حجم جست‌وجو، سختی، CPC، traffic، backlink و ranking: `DATA NOT AVAILABLE`.
- نتیجه‌های SERP این سند observation کیفی در تاریخ مشخص هستند، نه forecast.
- هیچ مقاله‌ای ایجاد یا منتشر نشد و هیچ تغییر product code در این مرحله انجام نشد.
- اولین cluster باید با یک مقاله B2B، یک راهنمای عملی ورودی تصویر و یک explainer category شروع شود؛ سپس بر اساس evidence و داده Search Console توسعه یابد.
- تولید انبوه مترادف‌ها، صفحه‌های thin، مقاله‌های AI بدون disclosure/evidence و claims مربوط به فیت/سایز/کاهش مرجوعی ممنوع است تا زمانی که مالک محصول آن‌ها را تأیید کند.
